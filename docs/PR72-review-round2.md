## 0. 뿌리 진단 — 왜 한 번에 이렇게 많이 나오는가

**(A) `deriveSchemeSwitchWeight` 는 사실 세트법과 무관하다.**
`scheme` 인자를 `build.pattern === 'extend'` 판정에만 쓴다(`js/domain.js:624-625`).
게다가 5개 스킴 **전부 기준(탑) 세트가 `repsDelta: 0`** 이라 `getSessionSetPlan` 의 `reps` 도 스킴에
따라 달라지지 않는다. 테스트 `set-schemes.test.mjs:1306-1307` 이 "세트법이 달라도 기준 무게는 같다"로
이를 못박는다. 즉 헤더 주석(`domain.js:596-602`)의 전제 — "새 세트법이 다른 반복을 처방하니 무게를
다시 잡아야 한다" — 는 **코드에서 성립하지 않는다.** 실제로 하는 일은
**"세트법 버튼을 누르면 최근 4세션 최고 e1RM 으로 무게를 다시 매긴다"** 는 별도의 증량/감량 채널이다.

**(B) 역산의 두 입력이 서로 다른 세트에서 온다.**
`roll.value` = 최근 4세션 **최대** e1RM(대개 가장 무겁고 반복이 적은 세트),
`reps` = **직전 세션 전 세트의 최대 반복**(대개 가장 가벼운 백오프 세트). 두 값이 짝이 아니다.

**(C) 카드·토스트가 `pendingReferenceSet`(남은 세트 중 최중량) 하나로 통일되면서,**
램프 스킴에서 탑세트를 완료하는 순간 "기준"이 백오프로 내려앉는다. 전환과 무관하게 표시·캡이 흔들린다.

이 셋을 고치면 아래 17건 중 12건이 함께 닫힌다.

# 1. Critical — 세트법을 만지지 않아도 발생

## #1 [Critical] 탑세트를 완료하는 순간 카드가 "무게 낮추기"로 뒤집힌다
`js/screens.js:3159, 3163-3177` — **워커 재현 확인**

`shown` 을 `prog.weight` → `pendingReferenceSet(exercise).weight` 로 바꾸고 라벨·색을
`shown vs prog.previousWeight` 비교로 판정하게 되면서, **램프 스킴(탑세트·역피라미드·피라미드)에서
탑세트를 끝내면 기준이 백오프로 내려가 카드가 하향으로 바뀐다.** 세트법 전환도, 실제 감량도 없다.

```
핵 스쿼트(compound_heavy 기본값 = 탑세트) 증량일, 세트 [top 95, backoff 85, backoff 85]

main: 세 시점 모두 '동일 무게 / 90'
```
'무게 낮추기'는 앱이 내린 적 없는 지시다. **고중량 복합 세션에서 가장 오래 노출되는 상태**이고,
세트법 기능을 한 번도 안 쓰는 사용자에게도 100% 발생한다.

## #3 [High] 반대 방향 — 더블 프로그레션 게이트를 우회한 증량, 세션마다 래칫

## #16 [Low·선행] override 별칭 키를 지울 수 없다 — 새 가드가 막다른 길로 만든다
`js/domain.js:786` vs `776` — 쓰기는 canonical 키만, 읽기는 `overrides[canonical] || overrides[exerciseName]`.
저장소에 `{'랫풀다운':'pyramid'}` 가 있으면 `setSetSchemeOverride('랫풀다운','straight')` 가 true 를 돌려주면서도

## #17 [Low·기존] 미완료 워밍업 세트 소실
`js/screens.js:2238-2248` — `warmup: doneSets.length === 0` 이라 워밍업을 1개라도 완료하면 남은 워밍업은

# 6. 테스트가 아직 못 잡는 경로 (427건 녹색인데 17건이 살아 있는 이유)

1. **역산 테스트가 전부 "단일 세션" 또는 "완전히 동일한 세션 2개" 로그**를 쓴다
   (`session('핵 스쿼트', 90, 8, 3)` × 2 등). 그래서 롤링 e1RM(4세션 최대)이 항상 직전 세션 실측과
   일치해 역산이 **항등식**이 된다 → #2·#3 이 구조적으로 드러날 수 없다.
   필요한 픽스처: **옛 세션이 더 강한 로그**(10일 전 90×8 / 3일 전 90×6), **세트마다 무게가 다른 로그**
   (탑 100×5 / 백오프 90×8).
2. **손수 "올린" 무게 케이스가 없다** — H-4 테스트는 `anchorWeight` 를 손으로 넘긴다(#4).
3. **드롭 전환 + 손수 조정 조합이 없다** — H-3 테스트(`1485`)는 조정 없이 통과한다(#5).
4. **경량 고립 S-3 테스트(`1408`)는 "유효 e1RM 전무"만 본다** (#6).
5. **카드 테스트(`1612`)는 세트를 완료하지 않은 상태만 본다** — 탑세트 완료 후 라벨이 뒤집히는 #1 미검증.
6. **완료 세트가 있는 드리프트 테스트가 없다**(`1447` 은 0개) (#12).
7. **`applyExerciseSwap` · `unskipExercise` 재구성 경로 미검증** (#10).
8. **`applyTopSetAutoDeload` × 세트법 전환 조합 미검증** (#11).
9. `rpt` 진행 중 전환, 미완료 워밍업 소실, 건너뛴 종목 카드·되살아남 미검증.

# 7. 권고

머지 전 최소 다음 3개를 고치면 12건이 함께 닫힌다.

1. **역산의 입력을 짝 맞추기** — `reps` 와 `roll.value` 를 같은 세트에서 뽑거나(기준 세트 = 최중량 세트의
   무게·반복), 아니면 **역산을 하향 재앵커 전용으로 좁힌다**(상향은 `prog.source === 'progress'` 인 날만).
   §0-(A) 때문에 "세트법마다 다른 강도"는 어차피 사다리가 만들므로 잃는 게 없다. → #2 #3 #4 #6 #12

   백오프로 내려가지 않게. → #1 #14
3. **가드를 실제 적용값(`ex.scheme`)으로, 그리고 차단 대신 분기로** — 재탭·남은 세트 없음 가드가
   드롭 추가와 접힘 복구를 막지 않게. → #7 #8 #9 #13
