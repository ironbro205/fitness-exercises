# AI 코칭 진단 + 앱 전체 개선점 발굴

> 조사일: 2026-08-08 · 대상: 헬스앱(fitness-exercises) v40 · **코드 수정 없음, 보고서 전용**
> 읽은 파일: `js/ai.js`(2109줄 전체), `js/domain.js`(1141줄 전체), `js/data.js`, `js/core.js`, `js/screens.js`(관련 구간)
>
> **용어 한 줄 풀이** — 이 문서에 자주 나오는 말
> - **프롬프트(prompt)**: AI에게 보내는 지시문. "너는 코치다, 이런 규칙으로 답해라" 같은 글.
> - **컨텍스트(context)**: 프롬프트에 함께 실어 보내는 사용자 데이터(운동 기록·1RM·체중 등).
> - **RIR (Reps In Reserve)**: 그 세트에서 "몇 개 더 할 수 있었나". RIR 2 = 2개 더 가능한 지점에서 멈춤.
> - **토큰(token)**: AI가 글을 세는 단위. 한국어는 대략 글자당 1~1.5토큰. 요금이 토큰 수로 매겨진다.
> - **프롬프트 캐싱**: 매번 똑같이 보내는 긴 지시문을 서버에 저장해 두고 재사용해 요금을 90% 아끼는 기능.

## 0. 요약

**AI 코칭의 "두뇌"(프롬프트·근거)는 이미 매우 좋다.** 볼륨·RIR·더블 프로그레션·디로드·부상 안전이 출처와 함께 프롬프트에 들어 있고, 코드 가드레일(`applySafetyGuardrail`, `clampRepsToClass`, 통증 게이트)이 AI의 실수를 마지막에 잡아준다. 간접 세트 0.5 카운팅, 세트 수 기반 볼륨 추적, "디로드는 성장 부스터가 아니다"라는 서술까지 **최신 근거와 교차검증한 결과 대부분 정확했다.**

문제는 다른 데 있다. 네 갈래다.

1. **실증된 버그 — 근성장 핵심 기전이 조용히 무너지고 있다.** 같은 운동이 두 이름으로 종목 풀에 노출되는 쌍이 9개 있고, 기록 조회는 이름 완전 일치라서 **띄어쓰기 하나로 점진적 과부하 추천이 65kg → 45kg(−31%)이 된다.** 통증 보고 후 증량을 막는 안전 게이트도 같은 이유로 뚫린다. 둘 다 테스트 하네스로 재현했다. (1-9)
2. **계산해 놓고 안 보여준다.** 앱은 부위별 주간 볼륨을 정확히 계산하지만 그 값은 **AI 프롬프트 안에서만** 산다. STATS 탭의 "부위별 분배"는 세션 타입 횟수일 뿐이다. 일일 AI 추천 기능(200줄 프롬프트)은 **호출부가 없어 통째로 죽어 있다.**
3. **근거가 낡거나 과한 지점 5개.** 특히 ①"같은 종목 6주 이상 → 교체"는 **근거 없는 통념**이고(Fonseca 2014·Baz-Valle 2019·Kassiano 2022가 반박), ②"부위당 주 2회 우월(Schoenfeld 2016)"은 **같은 저자들이 2019년 25개 연구로 뒤집었다**(볼륨 동일 시 빈도 무관). ③정체 판정 문턱(3세션)은 측정 잡음(CV 4.2%)보다 신호가 작아 원리상 거짓양성이 난다. (1-11)
4. **목표(린매스)의 절반이 비어 있다.** `COACH_KNOWLEDGE`는 섹션 번호가 **3 → 6으로 건너뛴다** — 영양 섹션 4·5번이 삭제된 흔적이다. "단백질"이 `data.js`에 **0회** 등장한다. (1-10)

**최우선 3건:** ① 종목 이름 정합성 복구(난이도 하, 실증된 버그) → ② 부위별 볼륨 화면 노출(이미 계산됨) → ③ 영양 — 지식 베이스 공백부터 메우고(난이도 하) 최소 추적 붙이기.

## 1. AI 코칭 기능별 진단

### 1-1. 코치 채팅 (`getCoachSystemPrompt` / `buildCoachSystemParts` / `callCoachAPI`)

**현재 상태**
- 시스템 프롬프트를 `stable`(역할·원칙·지식베이스·답변규칙)과 `dynamic`(부상 블록·기억 노트·사용자 데이터) 두 덩어리로 쪼개고, `stable`에만 `cache_control: ephemeral`을 걸었다. **구조적으로 정확한 캐싱 설계다.**
- `stable` 블록 크기: 코치 원칙(약 3.6KB) + `COACH_KNOWLEDGE`(약 6.4KB) ≈ 한글 3,300자 ≈ **대략 3,000~4,500토큰**. Claude Sonnet 5의 캐시 최소 단위 1,024토큰을 여유 있게 넘겨 캐싱이 실제로 걸린다.
- 세트 사이 채팅(`callSessionCoachAPI`)이 **같은 `stable` 문자열**을 재사용해 캐시를 공유한다. 잘 짜여 있다.

**문제**

| # | 문제 | 근거 |
|---|---|---|
| A | **메인 코치 채팅이 스트리밍이 아니다.** `callCoachAPI`는 `stream` 없이 통째로 기다린다(`max_tokens: 1024`). 세트 사이 채팅에는 이미 스트리밍(`callSessionCoachAPI` + `parseSSEStream`)이 구현돼 있는데 메인 채팅만 빠졌다. | `js/ai.js:669-719` vs `js/ai.js:1994-2058` |
| B | **캐시 TTL이 기본 5분.** 운동 중 쉬는 시간마다 코치에게 말을 걸면 간격이 3~10분이라 캐시가 자주 만료되고, 만료될 때마다 1.25배 쓰기 요금을 다시 낸다. | `cache_control: { type: 'ephemeral' }` — `ttl` 미지정 = 5분 |
| C | **`effort` 파라미터 미사용.** Sonnet 5는 `output_config: { effort: 'low'~'max' }`를 지원하고 **기본값이 `high`**다. 앱은 한 번도 지정하지 않으므로 "안녕?" 같은 가벼운 질문에도 최고 강도로 돈다. | 전 호출부에 `output_config` 없음 |
| D | **기억 노트 자동 저장이 폐지됐는데 파서가 남아 있다.** `parseCoachMemoryBlock`은 테스트에서만 호출되고 실제 흐름에서는 죽은 코드다. 코치가 대화 중 알게 된 부상·선호를 기억하려면 사용자가 직접 "기억 노트"에 타이핑해야 한다. | `js/screens.js:3621` 주석 "자동 기억 저장 폐지 — 수동 입력만" |

**개선안 (프롬프트/파라미터 수정 방향)**

- **A → 메인 코치 채팅도 스트리밍으로.** `callSessionCoachAPI`의 SSE 처리 코드를 그대로 재사용하면 된다(`parseSSEStream`은 이미 순수 함수로 분리·테스트돼 있음). 체감 대기시간이 3~8초 → 0.5초로 줄어든다.
- **B → 코치 `stable` 블록만 `ttl: "1h"`로.**
  ```js
  cache_control: { type: 'ephemeral', ttl: '1h' }
  ```
  손익 계산: 1시간 캐시는 쓰기 2배·읽기 0.1배라 **3회 이상 읽으면 이득**. 60분 운동 중 코치에게 4~6번 말을 거는 실제 사용 패턴이면 5분 TTL(쓰기 1.25배 × 3~4회 ≈ 5.2배)보다 1시간 TTL(2배 + 읽기 0.5배 ≈ 2.5배)이 **약 2배 싸다.**
  단, 루틴 생성(`generateFullRoutine`)처럼 하루 한 번짜리 호출은 **5분 유지**가 맞다(재생성·수정 대화가 5분 안에 몰리므로).
- **C → 호출별 `effort` 지정.**
  | 호출 | 권장 effort | 이유 |
  |---|---|---|
  | 코치 채팅 | `medium` | 대화 품질 유지하며 토큰 절감 |
  | 세트 사이 채팅 | `low` | 1~3문장 즉답이 요구사항 |
  | 루틴 생성 | `high`(또는 thinking 재활성화, 1-2 참조) | 다중 제약 최적화 |
  | 주간 리뷰·정체기 | `medium` | JSON 구조 출력 |
  | 신호 추출(haiku) | 해당 없음 | Haiku 4.5는 effort 미지원 |
- **D → "기억 후보 제안" 방식 복원.** 자동 저장을 되살리는 대신, 코치 응답에서 부상·선호 신호가 잡히면 **"이거 기억해 둘까요?" 버튼 한 개**를 띄우는 방식이 안전하다(세트 사이 채팅의 `sessionChatPending` 확인 UX가 이미 같은 패턴으로 동작 중이라 재사용 가능).

### 1-2. 루틴 생성 (`generateFullRoutine`)

**현재 상태 — 이 앱에서 가장 잘 만들어진 부분**
- 13개 원칙(안전 → 부족 부위 폐루프 → 다양성 → 종목 수 → RIR → 반복범위 → 더블 프로그레션 → 무게 스냅 → 간접 세트 보정 → 신장 강조 → 순서 → 컨디션 → 디로드)이 **각각 출처와 함께** 명시돼 있다.
- "목표 N세트까지 N세트 더" 형태로 **볼륨 격차를 숫자로 넘겨주는 폐루프**가 구현돼 있다(`volNeedNote`). 이건 상용 앱에서도 드문 수준이다.
- 종목 풀을 `EXERCISE_BODY_PART_MAP`에서 동적 생성하고 `[메인가능]`·`[신장강조]` 태그를 붙여 넘긴다 → AI가 풀 밖 종목을 지어내는 걸 구조적으로 막는다.
- 응답 후 `applySafetyGuardrail`이 금기 종목을 코드에서 한 번 더 걸러낸다(프롬프트를 어겨도 사용자 화면까지 못 옴).
- 소프트/하드 기준을 구분해 서술한다("수확 체감이지 금지선이 아니다") — 과학적으로 정직한 서술.

**문제**

| # | 문제 | 근거 |
|---|---|---|
| E | **`thinking: { type: 'disabled' }`가 전 호출에 적용돼 있다.** v40 핫픽스에서 "Sonnet 5 기본 생각모드가 max_tokens를 소진해 빈 응답"이 나서 껐다. 그런데 루틴 생성은 13개 제약을 동시에 만족시켜야 하는 **전형적인 다중 제약 최적화 문제**로, 생각이 품질에 가장 크게 기여하는 종류의 작업이다. | `js/ai.js:1090` |
| F | **`focusBodyPart` 필터가 하체 세션에서 복근을 끌어온다.** `partKeysByGroup.legs`에 `abs`·`obliques`가 포함돼 있어 LEGS 루틴 컨텍스트에 복근 1RM이 딸려 들어간다. 의도된 것일 수 있으나, 프롬프트의 "LEGS = 하체/코어" 정의와 종목 풀 정의가 이 부분에서만 겹친다. | `js/ai.js:502`, `js/ai.js:884` |
| G | **`oneRMData` 변수가 `modifyRoutineWithAI`에서 선언만 되고 미사용** (죽은 코드 1줄). | `js/ai.js:56` |

**개선안**

- **E → thinking을 끄는 대신 예산을 늘리는 쪽이 정석.** Claude Sonnet 5에서 `max_tokens`는 **생각 + 답변을 합친 총 상한**이다. 즉 v40 버그의 진짜 원인은 "생각모드"가 아니라 **`max_tokens: 2048`이 너무 작았던 것**이고, 당시 조치로 4096까지 올렸으면서 생각은 계속 꺼둔 상태다. 권장:
  ```js
  // 루틴 생성 (generateFullRoutine)
  thinking: { type: 'adaptive' },
  output_config: { effort: 'high' },
  max_tokens: 10000,   // 생각 + 7종목 JSON이 함께 들어갈 여유
  ```
  **반드시 A/B로 검증할 것** — 실제 API 호출로 (a) 현재 설정, (b) 위 설정 두 개를 같은 부위로 3회씩 돌려 "부족 부위 반영 여부 / 무게 스냅 정확도 / 반복범위 준수"를 비교한다. 품질 차이가 없으면 현행 유지가 맞다(토큰 절감).
  ※ 가벼운 호출(신호 추출·세트 사이 채팅)은 지금처럼 thinking 꺼두는 게 맞다.
- **F → 의도 확인 후 문서화.** 코어를 LEGS에 붙이는 게 의도면 프롬프트 주석에 명시, 아니면 `abs`/`obliques`를 별도 슬롯으로 분리.

### 1-3. 일일 추천 (`fetchAIRecommendation` / `loadAIRecommendationIfNeeded`) — **⚠️ 죽은 기능**

**현재 상태: 작동하지 않음.**

- `loadAIRecommendationIfNeeded()`는 **어디서도 호출되지 않는다.**
- `window.refreshAIRecommendation`은 전역에 노출돼 있지만 **어떤 `onclick`에서도 호출되지 않는다.**
- `state.aiRecommendation`을 **화면에 그리는 코드가 없다.**

```
$ grep -rn "loadAIRecommendationIfNeeded\|refreshAIRecommendation" js/ index.html
js/ai.js:1175      async function loadAIRecommendationIfNeeded()   ← 정의만
js/screens.js:3439 window.refreshAIRecommendation = ...            ← 정의만
```

즉 **200줄이 넘는 프롬프트(과학 근거·추천 로직·다양성 회피 이력·안전 블록)가 통째로 사문화**돼 있다. 대신 운동 화면 STEP 1은 룰 기반 `recommended` 변수(이번 주 세션 타입 횟수 최소값)만 쓴다.

**놓치고 있는 것:** 이 프롬프트는 컨디션(RPE≥8.5 → light), 사이클 단계(디로드 → light), 부족 부위, 최근 추천 다양성까지 반영하도록 이미 설계돼 있다. 룰 기반 대체물은 이 중 **아무것도** 반영하지 않는다.

**개선안 (두 갈래 — 하나 골라야 함)**

- **(a) 되살리기**: 홈 화면 상단 또는 운동 STEP 1에 "오늘의 추천" 카드를 넣고 `loadAIRecommendationIfNeeded()`를 호출. 캐시가 날짜 기준이라 하루 1회만 API를 쓴다(비용 부담 낮음).
- **(b) 정리하기**: 룰 기반 추천으로 충분하다고 판단되면 `fetchAIRecommendation`·`loadAIRecommendationIfNeeded`·`refreshAIRecommendation`·`KEYS.AI_RECOMMENDATION*`를 제거해 코드/테스트 골든 심볼을 줄인다.

**권장: (a)** — 이유는 3-1 참조.

### 1-4. 주간 리뷰 (`generateWeeklyReview` / `shouldShowWeeklyReview`)

**현재 상태**
- 이번 주 운동 횟수·세션 타입·체중·PR·부위별 볼륨(그룹 합산)·컨디션을 모아 S~D 등급과 wins/improvements/nextWeek/coachNote를 받는다.
- 평가 기준에 큰 근육/작은 근육 임계를 분리해 넣었고 종아리 예외까지 명시했다 — `getVolumeDiagnosis`와 기준이 일치한다.

**문제**

**개선안**

### 1-5. 정체기 분석 (`detectPlateauSignals` / `analyzePlateauWithAI`)

**현재 상태**
- 규칙 기반 pre-check로 신호 2개 이상일 때만 AI를 부른다(비용 절약 설계, 좋음). 캐시 3일.
- 신호 3종: `pr_stalled`(2주 PR 없음), `weight_stalled`(2주 체중 변화 <0.3kg), `frequency_drop`(최근 7일 운동 < 목표−1).

**문제 — 이 기능이 AI 코칭 중 가장 약하다**

| # | 문제 | 상세 |
|---|---|---|
| K | **이미 계산해 둔 정확한 정체 신호를 안 쓴다.** `buildUserContext`는 종목별로 "최근 3세션 무게 동일 **AND** 본세트 최고 반복도 비상승"을 판정해 `recentLifts[name].plateau`에 담아둔다. 이게 진짜 정체 신호다. 그런데 `detectPlateauSignals`는 이 값을 전혀 참조하지 않고 대리지표 3종만 본다. | `js/ai.js:331-346` vs `js/ai.js:1497-1536` |
| L | **`weight_stalled`는 린매스 목표에서 오진 위험이 크다.** 체중이 2주간 안 변하는 것은 리컴포지션(체지방↓ + 근육↑) 진행 중일 때 **정상이자 오히려 바람직한** 상태다. 이걸 "정체기 신호"로 세는 건 목표와 어긋난다. | `js/ai.js:1512-1522` |
| M | **`pr_stalled`는 더블 프로그레션과 충돌한다.** PR은 `maxWeight > ex.lastWeight`일 때만 기록된다. 더블 프로그레션은 **무게를 고정하고 반복을 올리는 기간**이 정상 진행인데, 그 기간엔 PR이 0이다. 즉 정상 진행 중에 "정체" 판정이 뜬다. | `js/screens.js:1490-1509` |
| N | **`bodyLog` 인덱스 기반 조회 버그(코치 컨텍스트 전반).** `buildUserContext`는 "1개월 전 체중"을 `bodyLog[length-30]`으로 잡는데, `bodyLog`는 **하루 1개씩만 쌓이는 게 아니라 사용자가 입력한 날만** 쌓인다. 주 2회 재는 사람이면 "30개 전"은 실제로 **약 15주 전**이다. 게다가 `bodyLog.length > 14`가 아니면 체중 변화를 아예 표시하지 않는다. | `js/ai.js:296-299` |

**개선안**

- **K → 정체 판정을 `recentLifts[].plateau` 기반으로 교체.**
  ```
  새 신호: lift_stalled = (plateau=true 종목이 2개 이상)
  ```
  이게 "무게도 반복도 안 오름"이라 진짜 정체를 잡는다. 기존 3종은 보조 신호로 강등.
- **L → `weight_stalled` 제거 또는 의미 반전.** 린매스 목표에서는 "체중 유지 + 1RM 상승 = 리컴포지션 성공"이므로, 오히려 **긍정 신호로 재해석**하는 게 맞다. 최소한 정체기 신호 목록에서 빼야 한다.
- **M → `pr_stalled`를 "반복도 무게도 2주간 상승 없음"으로 재정의.** 반복 상승은 `recentLifts[].history[].reps`로 이미 추적 가능하다.
- **N → 날짜 기반 조회로 교체.** `bodyLog.find(b => b.date <= 30일전)` 형태로 바꾸고, 표본이 적으면 "표본 부족" 표기(컨디션 추이가 이미 쓰는 패턴).

### 1-9. 종목 이름 정합성 — **실증된 버그 2건** ⚠️

조사 중 테스트 하네스(`tests/_harness.mjs`)로 **실제 코드를 돌려 확인한** 문제다. 추정이 아니라 재현 결과다.

#### 버그 1 — 별칭 종목 9쌍이 종목 풀에 중복 노출 → 점진적 과부하가 무너진다

`EXERCISE_BODY_PART_MAP`에는 같은 운동이 두 이름으로 들어 있는 쌍이 **9개** 있다:

```
"체스트 프레스 머신" == "머신 체스트 프레스"      "랫풀다운" == "랫 풀 다운"
"펙덱 플라이" == "머신 펙 덱 플라이"            "시티드 로우 머신" == "머신 시티드 로우"
"숄더 프레스 머신" == "머신 시티드 숄더 프레스"    "해머 컬" == "덤벨 해머 컬"
"사이드 레터럴 레이즈" == "덤벨 사이드 레터럴 레이즈"  "레그 익스텐션" == "머신 레그 익스텐션"
"트라이셉스 푸시다운" == "케이블 푸시 다운"
```

`getExercisePoolFor()`는 이 맵을 그대로 순회해 종목 풀을 만들므로, **AI에게는 두 이름이 서로 다른 종목으로 보인다.** 그리고 프롬프트는 "풀에 없는 종목 사용 금지"라 AI가 둘 중 아무 쪽이나 고른다.

문제는 진행도 조회가 **이름 완전 일치**로만 동작한다는 것이다(`js/domain.js:88,105,116,122`).

**재현 결과** — 사용자가 `랫풀다운` 60kg × 12회를 2세션 연속 수행한 상태에서:

| AI가 처방한 이름 | 추천 결과 | 판정 |
|---|---|---|
| `랫풀다운` | `source=progress`, **65kg** ("지난 60kg × 상단 12회 달성 → 65kg") | 정상 |
| `랫 풀 다운` | `source=rm_estimate`, **45kg** ("1RM 추정 기반 (첫 시도)") | **기록 유실** |

같은 운동인데 **띄어쓰기 하나로 65kg → 45kg (−31%)**. 점진적 과부하는 이 앱이 근성장을 만들어내는 핵심 기전인데, 그게 조용히 리셋된다.

**게다가 안전 게이트도 같이 뚫린다.** `hasRecentPain`도 완전 일치라서:

| 통증 보고 종목 | 조회 이름 | 결과 |
|---|---|---|
| `랫풀다운` | `랫풀다운` | `true` → 증량 차단 ✅ |
| `랫풀다운` | `랫 풀 다운` | `false` → **통증 있는데 증량 허용** ⚠️ |

**같은 코드베이스 안에서 일관성이 깨져 있다는 게 결정적 증거다.** 1RM 계열은 별칭을 정규화한다(`calculateRollingMax1RM`의 `EXERCISE_ALIASES_1RM[ex.name] || ex.name`, `get1RM`의 3단계 조회). 반면 진행도·통증·자극·채팅 신호 조회는 정규화가 없다. 즉 설계 의도가 아니라 **누락**이다.

영향받는 함수: `_buildRecentSetsMap` / `getLastPerformedSets` / `getRecentPerformances` / `hasRecentPain` / `getRecentFeel` / `_recentChatSignals`, 그리고 `buildUserContext`의 `recentLifts` 집계(같은 운동이 두 줄로 표시됨).

**노출 빈도가 높다.** `SESSIONS` 폴백 템플릿(API 키 없을 때 쓰는 기본 루틴)의 PUSH 6종목이 **전부 별칭 표기**다(`체스트 프레스 머신`, `인클라인 덤벨 프레스`, `숄더 프레스 머신`, `사이드 레터럴 레이즈`, `펙덱 플라이`, `트라이셉스 푸시다운`). 템플릿으로 운동하다 AI 루틴으로 넘어가면 전 종목 기록이 갈린다.

#### 버그 2 — `인클라인 덤벨 프레스`가 부위 매핑에서 `null` → 볼륨에서 통째로 누락

```
getExercisePart('인클라인 덤벨 프레스')  →  null
```

`EXERCISE_ALIASES_1RM`에는 있지만 `EXERCISE_BODY_PART_MAP`에는 없고, 퍼지 매칭(부분 일치 → 키워드 추측)도 전부 빗나간다(어순이 `덤벨 인클라인 벤치 프레스`와 달라 부분 일치 실패, 키워드 목록에 `프레스` 단독 항목 없음).

결과: **이 종목의 세트는 `getRecentVolumeByPart`에서 가슴 볼륨으로 한 세트도 잡히지 않는다.** 그런데 이 종목은 PUSH 폴백 템플릿에 들어 있고, 가슴 상부(`chest_upper`) 매핑 종목은 통틀어 2개뿐이다. 즉 가슴 상부 볼륨이 실제보다 낮게 보고되고, AI는 "가슴 부족"으로 오판해 불필요하게 가슴을 더 넣는다.

**수정 방향 (둘 다 작다)**
1. 조회 함수들에 정규화 한 줄 추가 — 이미 있는 별칭 테이블을 쓰면 된다:
   ```js
   function canonicalName(n) { return EXERCISE_ALIASES_1RM[n] || n; }
   ```
   `_buildRecentSetsMap`의 키와 조회, `hasRecentPain`/`getRecentFeel`/`_recentChatSignals`의 비교를 이 함수로 감싼다.
2. 종목 풀 생성 시 별칭을 제외해 **표준명만** AI에게 보여준다(`getExercisePoolFor`에서 `EXERCISE_ALIASES_1RM`에 키로 등장하는 이름은 건너뛰기). 또는 근본적으로 `EXERCISE_BODY_PART_MAP`에서 별칭 항목을 지우고 `getExercisePart`가 별칭 테이블을 거치게 한다.
3. `인클라인 덤벨 프레스`를 `EXERCISE_BODY_PART_MAP`에 추가하거나(표준명 `덤벨 인클라인 벤치 프레스`로) `getExercisePart`가 별칭 테이블을 먼저 조회하게 한다.

**검증 방법:** 위 재현 스크립트를 `tests/characterization.test.mjs`에 회귀 테스트로 추가하면 재발을 막는다.

### 1-10. 코치 지식 베이스의 **영양 공백** — 목표(린매스)의 절반이 비어 있다

`COACH_KNOWLEDGE`(`js/data.js:898~947`)의 섹션 번호를 보면 이렇다:

```
### 1. 트레이닝 핵심 원리      ### 6. 보충제 (근거 등급순)
### 2. 종목 자세(폼) 핵심 큐    ### 7. 회복 — 수면·디로드·부위 회복
### 3. 부상·통증 대응          ### 8. 워밍업·가동성
        ↑ 4번, 5번이 없다      ### 9. 강도·진행 기법
```

**4번과 5번이 통째로 비어 있다.** 번호를 재정렬하지 않은 채 남아 있는 걸로 보아, FUEL 탭을 걷어낼 때 영양 관련 두 섹션을 삭제하고 나머지를 그대로 둔 흔적이다.

정량 확인:
- `js/data.js`에서 **"단백질" 등장 0회**
- `js/ai.js`에서 1회 — 그것도 코치 원칙 5번의 이 문장이다:
  > "체지방을 빼는 시기에도 근육을 지키려면 웨이트를 병행하고 단백질을 충분히 확보하라고 조언할 수 있다**(앱에 영양 추적 기능은 없으니 일반 텍스트 조언으로만)**."

**결과:** 훈련 주제는 전부 출처가 달린 큐레이션 지식으로 답하는데, **영양 주제만 모델의 일반 지식으로 답한다.** "단백질 얼마나 먹어야 하나요?" 같은 가장 흔한 질문에 대해 이 앱은 아무 근거도 쥐여주지 않는다. 목표가 "린매스(체지방↓ + 근육↑)"인 앱에서 이건 절반이 비어 있는 것이다.

**개선안 (기능 개발과 무관하게, 프롬프트만으로 즉시 가능):** `COACH_KNOWLEDGE`에 4·5번 자리를 채운다. 조사로 확보한 근거는 3-3에 정리했다. 이건 **난이도 하 / 효과 즉시**인 유일한 영양 개선이므로, 4번 백로그(영양 추적 기능, 난이도 상)와 분리해 **먼저** 하는 게 맞다.

### 1-11. 근거 재검증 — 프롬프트·로직이 최신 근거와 어긋나는 지점 3건

앱의 근거 수준은 전반적으로 높지만, 웹 조사로 교차검증한 결과 **명확히 틀렸거나 과도한** 지점 3개가 나왔다.

#### ① "같은 종목 6주 이상 → 종목 교체" — **근거 없는 통념이다** ❌

```js
// js/ai.js:1566 — analyzePlateauWithAI 시스템 프롬프트
'- 자극 적응: 같은 종목 6주 이상 → 종목 교체\n'
```

**어떤 RCT도 "N주 후 종목을 바꿔야 한다"는 시간 임계값을 확립한 적이 없다.** 오히려 반대 방향의 근거가 있다:

- **Fonseca 2014** (JSCR 28(11):3085-3092, n=49, 12주): 종목을 **12주간 완전히 고정한 군**도 대퇴사두 CSA 11.6~12.0% 증가 — 종목 변화 군과 **전체 크기 증가는 차이 없음**. 다만 종목 고정 군은 대퇴사두 일부 갈래를 놓쳤다.
- **Baz-Valle 2019** (PLoS One 14(12):e0226989, 훈련자 21명, 8주): 매 세션 무작위 종목 변경 vs 고정 → 1RM·근두께 **군간 차이 없음**. 오히려 **중간광근은 고정 군에서만** 유의 증가. 변화 군의 유일한 유의 이점은 **내적 동기**였다.
- **Kassiano 2022** (JSCR 36(6):1753-1762, 체계적 고찰 8편): *"**체계적인** 변화는 국소 비대와 근력을 향상시킬 수 있다. 반면 **과도하고 무작위적인** 변화는 근육 발달을 저해할 수 있다."*

**게다가 이 규칙은 앱 자신의 다른 기능과 충돌한다.** 종목이 바뀌면 `getRecentPerformances` 히스토리가 끊겨 더블 프로그레션 추적선 자체가 사라진다(1-9의 별칭 버그와 같은 메커니즘).

**수정 방향:** 이 줄을 삭제하고 **해부학·통증·동기 기준**으로 대체한다.
```
- 자극 적응: (삭제)
- 종목 교체는 시간이 아니라 사유로 판단한다:
  (a) 해부학적 공백 — 루틴이 특정 근육 갈래·각도를 못 덮을 때
  (b) 통증·장비 제약
  (c) 진짜 정체 확정 시 (아래 ③ 기준 충족)
  (d) 최근 4주 세션 완수율 하락 = 동기 저하 → 이때만 "새 종목"을 제안하되,
      이유를 "근성장"이 아니라 "재미·지속"으로 정직하게 설명 (Baz-Valle 2019)
- 진행 중인 종목은 최소 8~12주 유지가 기본. e1RM이 오르는 중이면 바꿀 이유가 없다.
```

#### ② e1RM 계산에 RIR이 빠져 있고, Epley는 종목별로 체계 편향이 있다

```js
// js/domain.js:36 — RIR 항이 없다
function calculate1RM(weight, reps) { return weight * (1 + reps / 30); }
var ROLLING_1RM_MAX_REPS = 12;  // 근거상 10이 상한
```

**문제 A — RIR 미반영 → 체계적 과소평가.** 모든 e1RM 공식은 "이 세트가 실패까지 갔다"를 전제한다. 그런데 이 앱은 프롬프트에서 **RIR 2~3을 목표로 처방**한다. 실패까지 안 간 세트를 그대로 대입하면 Epley 기준 **RIR 1당 약 2~3% 과소평가**된다.

| 실제 수행 | e1RM 과소평가 |
|---|---|
| 8회 @ RIR 2 | −5.0% |
| 8회 @ RIR 3 | −7.3% |
| 10회 @ RIR 4 | −9.1% |

즉 앱이 계산하는 1RM은 사용자의 실제 능력보다 **5~9% 낮게** 잡혀 있고, 그 1RM에 다시 0.62~0.75를 곱해 작업 무게를 추천하니 **오차가 누적**된다.

**문제 B — Epley의 종목별 편향.** Nuzzo 2024(Sports Medicine, 269개 연구·7,289명 메타회귀)에 따르면 **종목이 유일하게 유의한 조절변수**다. 같은 %1RM에서 가능한 반복수가 종목마다 크게 다르다:

| %1RM | 벤치프레스 | 레그프레스 |
|---|---|---|
| 70% | 14.1회 | **19.0회** |
| 80% | 8.8회 | **13.1회** |

Epley를 그대로 쓰면 상체 프리웨이트는 ±3%로 꽤 정확하지만 **하체 머신류는 +15% 안팎 과대평가**한다. 이 앱의 `INITIAL_1RM`은 레그프레스 216kg인데, 이 값이 부풀려져 있을 가능성이 높다.

**문제 C — 반복수 상한이 12회.** 연구 정설은 **10회 이하**(Reynolds 2006: 5RM이 가장 정확, 반복수 증가 시 정확도 급락 / Mayhew 2008: 10회 미만에서 확실히 더 정확).

**수정 방향 (우선순위 순)**
1. **가장 중요:** e1RM 절대값을 종목 간 비교·합산하지 않고 **같은 종목 내 시간 추세로만** 쓴다. 종목별 체계 편향은 자기 자신과 비교하면 상쇄되므로, 이게 가장 안전하고 근거가 확실한 사용법이다. — **이미 앱이 대체로 이렇게 쓰고 있다** (`calculateRollingMax1RM`이 종목별 롤링 최대). ✅ 유지
2. RIR 실측을 받게 되면(백로그 #7) 공식에 반영: `w × (1 + (reps + RIR)/30)`
3. `ROLLING_1RM_MAX_REPS`를 12 → **10**으로
4. 1RM 화면에 한 줄: *"추정치입니다. 종목에 따라 10~15% 차이날 수 있어요."*
5. 종목별 분모 보정(상체 30, 하체머신 45)은 **권하지 않는다** — 레그프레스는 반복 구간에 따라 역산 분모가 44~81로 흔들려 고정 보정이 잘 안 맞는다. 3·4번이 더 안전하다.

#### ③ 정체 판정 문턱이 통계적으로 너무 낮다

앱의 현재 판정: **"최근 3세션 무게 동일 + 최고 반복 비상승"**(`buildUserContext`) / 정체기 신호 2개 이상(`detectPlateauSignals`).

**측정 잡음이 그 신호보다 크다.**
- **Grgic 2020** (Sports Med Open 6:31, 체계적 고찰): 1RM 검사–재검사 **변동계수(CV) 중앙값 4.2%**.
- 비선수 중급자의 현실적 e1RM 증가율은 **주당 0.25~1%** → 4주면 1~4%.
- **즉 4주치 데이터로는 "정체"와 "정상 진행"을 통계적으로 구분할 수 없다.** 기대 증가폭이 측정 잡음보다 작기 때문이다.
- Hopkins(2004, Sportscience 8:1-7): 두 시점 단순 비교로 실제 변화라 말하려면 ≈ **2.77 × TE** = 약 11.6% 변화가 필요. 3세션 평균을 쓰면 표준오차가 2.4%로 줄어든다.

> **참고:** 흔히 인용되는 "1RM은 하루 ±18% 변동"(Flanagan & Jovanović 2014)은 **동료심사를 거치지 않은 실무 저널** 출처라 설계 기준으로 쓰면 안 된다. Grgic의 4.2%가 타당한 기준이다.
>
> **정직한 한계:** "몇 세션 정체하면 진짜 정체"에 대한 **직접적인 연구 기준은 존재하지 않는다.** 아래 표는 측정학 원칙(TE·SWC)에서 도출한 것이지 RCT 결과가 아니다.

**수정 방향 — 3단계 신뢰도로 분리하고 "정체입니다" 단정을 피한다**

| 단계 | 조건 | 사용자에게 보이는 것 | 행동 |
|---|---|---|---|
| 관찰 | 최근 3세션 평활 e1RM이 직전 3세션 대비 +1% 미만 | 배지만 (경고 X) | 없음 |
| 주의 | **6세션 이상 & 4주 이상** 추세 기울기 ≤ 0 | "정체 주의" | 원인 점검 질문(수면·완수율·부위 세트 수) |
| 확정 | **8세션 이상 & 6주 이상** + 같은 무게 반복 미증가 **또는** 같은 반복 RIR 상승 | "정체" | 개입 제안 |

**최소 데이터 가드:** 종목당 6세션·4주 미만이면 **정체 판정 자체를 금지**.
**개입 우선순위** (종목 교체는 마지막): ① 회복 점검(수면·섭취·완수율) → ② 디로드 1주 → ③ 해당 부위 주간 세트 수 조정 → ④ 종목 변경(해부학적 사유로 설명).

#### ④ "부위당 주 2회 자극이 1회보다 우월" — 같은 저자들이 2019년에 뒤집었다

이 문장이 **4곳**에 들어 있다:

```
js/data.js:901  '- 빈도: 같은 부위 주 2회 자극이 1회보다 우월. 주간 볼륨이 같다면 2회 분할이 유리 (Schoenfeld 2016 메타).'
js/ai.js:118    '- 부위당 주 2회 자극 우월 (Schoenfeld 2016)'          ← 루틴 수정
js/ai.js:747    '- 부위당 주 2회 자극이 1회보다 우월 (Schoenfeld 2016)'   ← 일일 추천
js/ai.js:1349   '- **운동 빈도**: 부위당 주 2회 자극 우월 (Schoenfeld 2016)' ← 주간 리뷰
```

**Schoenfeld·Grgic·Krieger 2019** (J Sports Sci 37(11):1286-1295, 25개 연구) — **2016년 메타의 같은 저자들**이 내린 결론:

> *"There is **strong evidence** that resistance training frequency does **not** significantly or meaningfully impact muscle hypertrophy **when volume is equated.** Thus, for a given training volume, individuals can choose a weekly frequency per muscle group **based on personal preference**."*

**즉 앱의 `data.js:901`은 정확히 반대로 적혀 있다.** "주간 볼륨이 같다면 2회 분할이 유리"가 바로 2019년 논문이 부정한 명제다. 2016년 메타에서 2회가 우월해 보였던 것은 **그 연구들에서 2회 군의 주간 볼륨이 더 높았기 때문**이라는 게 현재 해석이다.

Pelland 2025/2026도 같은 방향이다 — 빈도 → **근비대** 효과는 "무시할 만한 수준과 양립 가능", 반면 빈도 → **근력**은 유의미(수확 체감 동반).

**수정 방향 — 주 2회 권고 자체는 유지하되 이유를 바꾼다.** ACSM 2026 포지션 스탠드도 주 2회 이상을 권고하지만, 근거상 정확한 이유는 "2회가 더 자라서"가 아니라 **"주간 총 세트를 세션당 생산적 구간 안에 나눠 담는 수단"**이기 때문이다(+근력 이득).

```
변경 전: 부위당 주 2회 자극이 1회보다 우월 (Schoenfeld 2016)
변경 후: 빈도 자체는 근비대에 거의 무관하다 — 주간 총 세트가 같으면
        주 1회든 2회든 근비대 차이가 없다 (Schoenfeld·Grgic·Krieger 2019, 25개 연구).
        그럼에도 주 2회를 권하는 이유는 두 가지다:
        (a) 근력에는 빈도가 유의미하고 (Pelland 2025),
        (b) 주간 세트를 한 세션에 몰면 세션 내 수확 체감 구간에 들어가므로
            나눠 담는 그릇이 필요하다.
        → 사용자가 주 1회 분할을 선호하면 막지 말고, 세션당 부위 세트 수만 점검한다.
```

#### ⑤ 주간 리뷰가 사용자에게 "🔥 과잉"과 "🟡 MEV"를 그대로 노출한다

```js
// js/ai.js:1324 — generateWeeklyReview
var status = vol < loV ? '🔴 부족' : (vol < mevV ? '🟡 MEV' : (vol <= optV ? '🟢 적정' : '🔥 과잉'));
```

두 가지 문제가 있다.

**(a) "과잉"은 근거를 넘어선다.** Pelland 2025/2026(67개 연구·2,058명)에서 볼륨→근비대 기울기가 0보다 클 **사후확률 100%**였고, **곡선이 꺾여 내려오는 지점은 확인되지 않았다.** 즉 주 20세트 초과는 "손해"가 아니라 **"이득 증가폭이 완만해지는 구간"**이다. Baz-Valle 2022의 "12~20세트" 권고도 정량분석에 **6편**만 들어갔고, 그중 삼두는 오히려 20세트 초과가 유의하게 더 좋았다(p=0.01).

**(b) "MEV"는 검증된 용어가 아니다.** MEV/MAV/MRV는 Israetel 외의 **자비 출판 서적**(*Scientific Principles of Hypertrophy Training*, RP 2021)에서 나온 휴리스틱이며, **그 수치 경계값을 검증한 동료심사 연구는 없다.** 사용자에게 과학 용어처럼 보여주면 안 된다.

**아이러니한 점:** `buildUserContext`는 **이미 정직하게** 적고 있다 — *"🔥 수확 체감 구간 (충분히 함 — 더 안 늘려도 됨, **하드컷 아님**)"*. 같은 앱의 두 프롬프트가 서로 다른 말을 한다.

**수정 방향:** 주간 리뷰의 라벨을 `buildUserContext` 쪽에 맞춘다.
```js
'🔴 부족'  →  유지 (하한 근거가 가장 단단함 — ACSM 2026: 주 10세트 이상)
'🟡 MEV'   →  '🟡 하한 미달'
'🟢 적정'  →  유지
'🔥 과잉'  →  '🔥 이득 완만'   // "여기서부터는 세트를 늘려도 이득 증가가 줄어요"
```

#### ✅ 반대로, 근거가 앱을 지지하는 것도 확인됐다

- **세트 수 기반 볼륨 추적이 옳다.** Baz-Valle 2021(JSCR 35(3):870-878, 14개 RCT 고찰)이 **"총 세트 수 세기"를 근비대 목적의 타당한 볼륨 정량화 방법**으로 결론냈다. 반면 **총 볼륨 부하(세트×반복×무게)는 나쁜 지표**다 — 무거운 종목과 가벼운 부하를 자동으로 우대하는 편향이 있다(SBS 2015). 앱이 톤수가 아니라 세트 수를 쓰는 건 **정확한 선택이다.**
- **간접 세트를 0.5로 세는 것도 옳다.** Pelland 외 2025/2026(Sports Medicine, DOI 10.1007/s40279-025-02344-w, PMID 41343037)은 보조근 세트를 1(total)/0.5(fractional)/0(direct) 세 방식으로 모델링해 비교했고, **0.5 방식의 상대적 근거가 가장 강했다**고 보고했다. 결론에서 *"Distinguishing between direct and indirect sets appears essential"*이라고 명시했다. `js/domain.js:846`의 주석 근거를 이 DOI로 정확히 갱신할 가치가 있다.
  ※ 단, 0.5는 **검증된 생리 상수가 아니라 여러 연구를 가장 잘 예측한 근사치**다. 앱 주석이 이미 "정밀값 아닌 휴리스틱"이라고 적어 둔 것도 정확하다.
- **디로드를 "성장 부스터가 아니다"라고 적은 것이 정확하다.** 루틴 생성 프롬프트 13번은 *"이 감량은 '성장 부스터'가 아니라 누적 피로·관절·부상 회복용이다(디로드가 근성장을 더 늘린다는 직접 근거는 약함)"*라고 쓴다. 이건 최신 리뷰와 정확히 일치한다 — Bell 외 2025(Strength & Conditioning Journal): *"There is a **clear absence** of high-quality experimental research elucidating the objective benefits of deloading."* 그리고 Coleman 외 2024(PeerJ 12:e16777, **공저자에 Israetel·Schoenfeld 포함**, 훈련자 39명)는 1주 완전 휴식 디로드가 근두께에 차이를 만들지 못했고 **근력은 오히려 연속 훈련군이 유리**했다고 보고했다.
  - 앱의 디로드 처방("종목 유지, 세트 −40~50%, RIR 3~4, 약 1주")도 Bell 2025 권고안(볼륨은 줄이고 **빈도는 유지**, 강도 소폭 감소, 5~7일)과 부합한다. **완전 휴식이 아니라 볼륨 감량**이라는 점이 특히 중요하다 — 부정적 결과를 낸 Coleman 2024는 완전 중단 조건이었다.
  - 홈 화면이 디로드 주차에 *"가볍게 · 건너뛰기 가능"*이라고 표시하는 것도 근거에 맞다.
  - **남은 개선점 하나:** 디로드 트리거가 순수 달력식(5주차 자동)이다. 근거 수준은 낮지만(설문·코치 관행) 자기조절 트리거가 더 합리적이다 — Rogerson 외 2024(Sports Med Open 10(1):26, 경쟁 선수 246명)에서 실제 트리거는 **수행 정체 · 근육통 증가 · 관절통**이었다. 앱은 `conditionLog`(RPE·컨디션)와 정체 신호를 이미 갖고 있으므로 붙이기 쉽다. 단 **연속 2회 이상 같은 방향**일 때만 발동시켜야 노이즈를 거른다.
- **세션당 부위 8세트 소프트 상한**도 방어 가능하나 단서가 있다. 흔히 인용되는 "세션당 6~8세트" 수치는 **휴식 2분 이상**이라는 조건이 붙은 값이고(Krieger 메타회귀), 휴식 90초 이하면 천장이 15~16세트로 두 배가 된다. 최신 Remmert 외 2025는 근비대 기준 **세션당 약 11 분할환산세트**를 제시한다(단 **SportRxiv 프리프린트, 동료심사 전**).
  - **실용 시사점:** 앱에 rest timer가 있는데 **실제 휴식 시간을 세트에 기록하지 않는다**(세트 객체는 `{weight, reps, isWarmup, completed}`). 휴식 시간을 기록하면 세션당 권장 상한을 조건부로 줄 수 있다.

## 3. 최우선 3건 상세 제안

선정 기준: **(근성장 임팩트 × 근거 확실성) ÷ 난이도**. 1번은 실증된 버그라 논쟁의 여지가 없고, 2번은 이미 계산된 데이터를 꺼내 보이는 일이며, 3번은 목표(린매스)의 비어 있는 절반이다.

### 3-1. 【최우선】 종목 이름 정합성 복구 — 점진적 과부하와 안전 게이트를 되살린다

**왜 1순위인가**
- **실증된 버그다.** 추정이 아니라 테스트 하네스로 재현했다(1-9).
- **근성장의 핵심 기전을 직접 망가뜨린다.** 점진적 과부하는 이 앱 전체가 그 위에 서 있는 원리인데, 띄어쓰기 하나로 65kg → 45kg(−31%)이 된다.
- **안전 문제이기도 하다.** 통증 보고 후 증량을 막는 하드 가드레일이 별칭에서 그냥 뚫린다.
- **난이도가 가장 낮다.** 이미 있는 별칭 테이블을 조회 지점에 끼우는 일이다.

**무엇이 문제인가 (한 줄 요약)**
`EXERCISE_BODY_PART_MAP`에 같은 운동이 두 이름으로 들어 있는 쌍이 9개 있고, 이게 AI에게 주는 종목 풀에 **둘 다** 노출된다. 그런데 기록 조회는 이름 완전 일치로만 동작한다.

**재현 결과 (실측)**

| 상황 | `랫풀다운`으로 처방 | `랫 풀 다운`으로 처방 |
|---|---|---|
| 진행도 추천 | `progress` · **65kg** | `rm_estimate` · **45kg** |
| 통증 게이트(통증 보고 후) | `true` → 증량 차단 | **`false` → 증량 허용** |

**추가 버그:** `getExercisePart('인클라인 덤벨 프레스')` → `null`. PUSH 폴백 템플릿에 들어 있는 종목인데 **가슴 볼륨에 한 세트도 안 잡힌다.**

**수정 방향 (3단계, 위에서부터)**

1. **조회 정규화** — `js/domain.js`에 헬퍼 하나를 추가하고 조회 지점에 적용한다.
   ```js
   function canonicalName(n) { return EXERCISE_ALIASES_1RM[n] || n; }
   ```
   적용 대상: `_buildRecentSetsMap`(맵 키 + 조회), `getLastPerformedSets`, `getRecentPerformances`, `hasRecentPain`, `getRecentFeel`, `_recentChatSignals`, 그리고 `buildUserContext`의 `recentLifts` 집계.
   ※ `calculateRollingMax1RM`과 `get1RM`은 **이미 정규화하고 있다** — 그 방식을 그대로 따르면 된다.
2. **종목 풀에서 별칭 제거** — `getExercisePoolFor()`가 `EXERCISE_ALIASES_1RM`의 **키로 등장하는 이름은 건너뛰게** 해서 AI에게 표준명만 보여준다. 그러면 AI가 애초에 별칭을 못 고른다.
3. **누락 매핑 추가** — `인클라인 덤벨 프레스`를 `EXERCISE_BODY_PART_MAP`에 넣거나(`덤벨 인클라인 벤치 프레스`와 동일 정보), `getExercisePart`가 별칭 테이블을 먼저 조회하게 한다. 후자가 재발 방지에 낫다.

**어떻게 확인하는가**
1. 위 재현 스크립트를 `tests/characterization.test.mjs`에 회귀 테스트로 넣는다 — 별칭 두 이름이 **같은** 추천 무게를 내는지 assert.
2. `node --test tests/characterization.test.mjs` 통과 확인.
3. 브라우저에서 PUSH 루틴을 AI로 생성 → 종목 풀에 `체스트 프레스 머신`/`머신 체스트 프레스`가 **하나만** 나오는지 확인.

**주의:** `EXERCISE_BODY_PART_MAP`에서 별칭 항목을 지우면 `tests/golden-symbols.json`과 기존 특성화 테스트가 깨질 수 있다. 골든 값 갱신이 필요한지 먼저 확인할 것.

### 3-2. 부위별 주간 볼륨을 사용자에게 보여준다 (STATS 탭)

**왜 2순위인가**
- **볼륨은 근비대 1순위 동력이다.** ACSM 2026 포지션 스탠드(137개 체계적 문헌고찰·3만 명 이상)가 "근비대는 **주 10세트 이상**에서 향상"으로 정리했고, Pelland 2025/2026(67개 연구·2,058명)에서 볼륨→근비대 기울기가 0보다 클 사후확률이 **100%**였다.
- **앱은 이미 정확히 계산하고 있다.** 새 로직을 만들 필요가 없다 — `getRecentVolumeByPart` → `groupVolumeBy` → `getVolumeDiagnosis`가 완성돼 있고, 간접 세트 0.5 카운팅까지 최신 근거(Pelland)와 일치한다.
- **그런데 그 값이 AI 프롬프트 안에서만 산다.** STATS 탭의 "부위별 분배"는 **세션 타입 횟수**(PUSH 5회 / PULL 4회)일 뿐, 근육 부위 세트 수가 아니다.

**지금 버려지고 있는 데이터 (주 4회 사용자 시뮬레이션 실측)**

```
삼두 6.8 · 가슴 6.0 · 이두 6.0 · 어깨전면 5.3 · 광배 4.5 · 등중부 4.5
대퇴사두 3.5 · 햄스트링 3.3 · 어깨후면 3.0 · 둔근 2.5 · 어깨측면 1.5   (주당 세트)

🔴 부족:     어깨 측면(1.5) · 대퇴사두(3.5) · 햄스트링(3.3) · 둔근(2.5)
🟡 하한미달: 가슴(6.0) · 삼두(6.8) · 이두(6.0) · 광배(4.5) · 등중부(4.5) · 어깨전면(5.3) · 어깨후면(3.0)
```

사용자는 "이번 주 4회 운동했다"만 보고 있는데, 실제로는 **하체가 절반 이하**이고 **어깨 측면이 거의 0**이다. 이걸 모르면 다음 루틴 선택이 개선될 수가 없다.

**수정 방향**

- STATS 탭에 "부위별 주간 볼륨" 카드 신설. 가로 막대 + 목표 범위 밴드 + 신호등.
- 라벨은 **`buildUserContext`의 정직한 표현**을 쓴다(1-11⑤ 참조): `부족` / `하한 미달` / `적정` / **`이득 완만`**(← "과잉" 아님).
- **직접 세트와 분할환산 세트를 둘 다** 보여준다. 사용자가 "가슴을 실제로 몇 세트 했나"와 "간접 포함 얼마인가"를 구분할 수 있어야 한다.
- **최소 표본 가드 필수** — 데이터가 2주 미만이면 판정하지 말고 "아직 판단하기 이릅니다"로. (현재 `getRecentVolumeByPart(2)`는 2주치를 무조건 2로 나눠 신규 사용자를 전부 "부족"으로 만든다 — 위 시뮬레이션에서 🟢 적정이 하나도 없는 것도 같은 이유다.)
- 한 줄 단서: *"이 범위는 연구 평균이고 본인 반응은 다를 수 있어요."*

**어떻게 확인하는가**
1. 로컬 서버(`python3 -m http.server 8000`)에서 STATS 탭 진입 → 부위별 막대가 뜨는지.
2. 데모 데이터 상태(운동 2회)에서 "판단 보류"가 뜨는지.
3. 프롬프트의 볼륨 숫자와 화면 숫자가 **일치**하는지 (둘 다 `getVolumeDiagnosis`를 쓰므로 일치해야 정상).

**기대효과:** 사용자가 스스로 부족 부위를 인지 → 루틴 선택이 개선됨. AI 추천을 "믿고 따르는" 관계에서 "이해하고 고르는" 관계로 바뀐다.

### 3-3. 영양 — 지식 베이스 공백부터 메우고, 최소 추적을 붙인다

**왜 3순위인가**
- 목표가 **린매스(체지방↓ + 근육↑)**인데 앱의 영양 데이터가 **0**이고, `COACH_KNOWLEDGE`는 섹션 4·5번이 **통째로 비어 있다**(1-10). "단백질"이라는 단어가 `data.js`에 **0회** 나온다.
- 근성장은 훈련과 영양 두 축인데, 이 앱은 훈련 축만 정교하다.
- **이 사용자 프로필은 리컴포지션에 유리한 쪽이다** — Barakat 2020(Strength Cond J 42:7-21)에 따르면 체지방 여유가 있고 상급자가 아닌 경우 성공 가능성이 높다.

**두 단계로 나눈다. 1단계는 난이도 "하"이므로 즉시 가능하다.**

#### 1단계 (즉시) — `COACH_KNOWLEDGE`에 영양 섹션 복원

프롬프트만 고치면 되므로 기능 개발 없이 오늘 할 수 있다. 채워 넣을 내용:

```
### 4. 영양 — 단백질
- 총량이 거의 전부다: 하루 1.6 g/kg 체중 부근에서 수확 체감이 시작된다
  (Morton 2018 BJSM, 49개 RCT·1,863명 — 1.62 g/kg 초과 시 제지방 증가분이 더 늘지 않음).
  Tagawa 2021(105편·5,402명)도 1.3 g/kg 아래에서 기울기가 급하고 위에서 완만해진다고 보고.
- 감량 중에는 더 높인다: 1.6~2.4 g/kg 체중 (Hector & Phillips 2018).
  Longland 2016(AJCN): 40% 적자 + 고강도 훈련 4주에서 2.4 g/kg 군은 제지방 +1.2kg / 지방 −4.8kg,
  1.2 g/kg 군은 +0.1kg / −3.5kg. 적자 중에도 근육이 늘 수 있다.
- ⚠️ "한 끼 20~30g 넘으면 낭비"는 틀린 통념이다. Trommelen 2023(Cell Rep Med):
  100g을 한 번에 먹어도 25g보다 근단백질 합성이 더 크고 더 오래 지속됐다.
  기존 상한설은 관찰 시간을 3~5시간으로 짧게 잡아 생긴 착시다.
- 분배(끼니당 0.4 g/kg)는 총량이 부족할 때만 의미가 있다. 원 출처(Schoenfeld & Aragon 2018)
  저자들도 추정치임을 인정했고 이후 연구는 엇갈린다(Hudson 2017: 균등 vs 편중 체성분 차이 없음).
  → 총량을 채웠으면 분배는 부차적이라고 답할 것.

### 5. 영양 — 에너지 균형과 리컴포지션
- 리컴포지션(체지방↓ + 근육↑ 동시)은 실제로 가능하다. 특히 초보·복귀자·체지방이 높은 사람에게서
  잘 일어난다 (Barakat 2020 Strength Cond J). 필수 조건은 ①점진적 과부하 ②충분한 단백질.
- ★적자 상한: 하루 500 kcal를 넘으면 제지방 증가가 사라진다
  (Murphy & Koehler 2022, Scand J Med Sci Sports 메타회귀).
- 감량 속도: 주 0.5~1.0% 체중. Garthe 2011(IJSNEM): 주 0.7% 감량군은 제지방 +2.1%,
  주 1.4% 감량군은 −0.2%로 정체. 두 군 모두 주 4회 웨이트를 했는데도 차이가 났다.
- 증량 시: 주 +0.25~0.5%, 유지 대비 +10~20% (Iraki 2019).
- ★단기 체중 변동은 지방이 아니다: 2주간 체중 변화의 84%가 제지방(주로 수분)이다
  (Bhutani 2017, Physiol Rep). 하루 체중으로 판단하지 말고 7일 이동평균을 쓸 것.
- 보충제: 근육량과 직접 연관되는 건 크레아틴 모노하이드레이트뿐이다(하루 3~5g, 로딩 불필요).
  IOC 합의(Maughan 2018) 기준 퍼포먼스 근거가 충분한 건 카페인·크레아틴·질산염·중탄산나트륨·
  (아마도) 베타알라닌 다섯뿐. 그 외는 근거가 약하다고 정직하게 답할 것.
```

그리고 코치 원칙 5번의 *"(앱에 영양 추적 기능은 없으니 일반 텍스트 조언으로만)"* 단서를 지운다.

#### 2단계 (기능) — "식단 기록기"가 아니라 **"체중 추세 + 단백질 체크"**

**중요: 전량 칼로리 기록을 만들면 안 된다.** 근거가 반대한다 — 앱 식단 기록은 섭취를 **10~27% 과소보고**하고(JMIR mHealth 2019 리뷰), 자가기록 행동은 시간이 지날수록 급감하며, 간소 기록 vs 전량 기록 RCT에서 6개월 체중 감소는 **5.7% vs 4.0%로 유의차가 없었다**(JMIR Form Res 2022;6(12):e42191).

**넣을 것은 3개뿐이다:**

| 순위 | 항목 | 입력 부담 | 근거 |
|---|---|---|---|
| 1 | **체중 → 7일 이동평균 → %/주** | 하루 3초 | Zheng 2015(Obesity, 17개 연구 전부에서 잦은 측정이 더 나은 결과), Bhutani 2017, Garthe 2011 |
| 2 | **단백질 4칸 체크** (끼니당 35g × 4) | 하루 4탭 | Morton 2018, Hudson 2017 |
| 3 | 훈련 진행 | **이미 있음** | Barakat 2020 |
| +α | 허리둘레 월 1회 | 월 1회 | 리컴포지션 중엔 체중이 안 변해서 체중만으론 성공을 놓침 |

**이 사용자(77.5kg) 기준 자동 계산값**
- 단백질 목표: **하루 140g** (1.8 g/kg) — 감량 모드면 **150~160g**
- 목표 체중 변화: **주 −0.4%(약 −0.3kg/주)**, 적자 300~350 kcal → Murphy & Koehler의 500 kcal 한계 안

**체중 추세 판정에서 반드시 지킬 것 (측정학)**
- 하루 체중 잡음 ±0.41kg(0.53% × 77.5) > 일주일치 신호 0.39kg → **단일 측정으로는 원리상 판단 불가**
- 이동평균 창은 **반드시 7의 배수** — 주말에 오르고 주중에 내리는 주간 리듬이 있다(Orsama 2014, Obes Facts)
- **데이터 14일 미만이면 판정 금지.** "아직 판단하기엔 일러요 (n일 더 필요)"
- 조정은 **3~4주에 한 번**. "이번 주 0.5kg 쪘다"로 칼로리를 건드리지 않기

**이건 1-11③(정체 판정)과 같은 원리다** — 신호보다 잡음이 크면 판정하지 않는다. 앱 전반에 이 원칙을 일관되게 적용하면 좋다.

**넣지 말 것:** 전 음식 칼로리 강제 기록 / 매일 체중 기반 즉시 칼로리 조정 / 체지방률 추정치 노출(공식 오차 ±4~5%p) / 탄수·지방 세분화 / 긴 보충제 목록.

**어떻게 확인하는가**
1. 1단계: 코치에게 "단백질 얼마나 먹어야 해?" / "한 끼에 30g 넘으면 소용없어?" 를 물어 **출처가 달린 수치**로 답하는지 확인.
2. 2단계: 체중을 며칠 입력해 보고 14일 미만에서 "판단 보류"가 뜨는지, 이동평균 선이 생값과 함께 그려지는지 확인.

## 5. 조사의 한계 (정직하게)

1. **API 호출로 실제 AI 응답 품질을 비교하지는 않았다.** 프롬프트·파라미터 검토와 코드 실행 검증까지만 했다. 특히 3-1의 thinking 재활성화(1-2 E)는 **반드시 A/B 실측이 필요**하다.
2. **세션당 세트 상한(11세트)의 최신 근거는 프리프린트**(Remmert 2025, 미심사)다. 앱 문구에 이 불확실성을 반영하는 게 좋다.
3. **"몇 세션 정체하면 정체인가"에 대한 직접 RCT는 없다.** 1-11③의 표는 측정학 원칙(TE·SWC)에서 도출한 것이지 실험 결과가 아니다.
4. **MEV/MAV/MRV 수치 경계값을 검증한 동료심사 연구를 찾지 못했다.** 없다고 단정하지는 않되, 현재로선 휴리스틱으로 취급하는 게 맞다.
5. **체지방률·유지 칼로리 추정치는 공식 기반**이라 각각 ±4~5%p, ±10~20% 오차가 있다. 3-3의 수치는 출발점이지 확정값이 아니다.
6. **Barakat 2020 원문(유료)은 확보하지 못했다.** 초록·NSCA 페이지·2차 요약으로 교차확인했고 결론은 일치했으나 세부 수치표는 직접 검증하지 못했다.
7. **세트 스킴 설계와 인클라인 트레드밀 걷기는 다른 조사가 담당하므로 의도적으로 다루지 않았다.**
